# 团队协作工作台

A single-process Fastify API, SQLite database and Vue static client. Requires Node 24.21.0.

```sh
npm ci
npm test
npm run typecheck
npm run build
```

Configure `HOST`, `PORT`, `DATABASE_PATH` and `APP_ORIGIN` as process environment variables (see `.env.example`), then run `npm start`. `APP_ORIGIN` is the exact browser origin, including scheme and port. The service is intended for a same-origin HTTPS reverse proxy; session cookies always use Secure, HttpOnly and SameSite=Lax. The current Vue client is a foundation scaffold.

To create the first administrator, build first and run the following in a local interactive terminal against an empty database:

```sh
node apps/api/dist/apps/api/src/cli/bootstrap-admin.js
```

The CLI asks for login, display name and a hidden password; it accepts no arguments or environment passwords. Further accounts are administrator-created and activated with a one-use ticket. Activation/reset tickets expire after 24 hours. Hand them to their owner securely; raw tickets are returned only on initial issuance. Retrying an issuance command with the same key returns metadata only. If the initial `POST /api/members` response is lost, replay the original create key and body to recover safe member ID/version metadata; the original raw ticket is not redisclosed. Then issue `POST /api/members/:id/reset` with a new `Idempotency-Key` and the current `expectedVersion`, including for a never-activated account. A stale version returns safe latest member/version metadata; use that current version with a fresh key. Issuing a new ticket invalidates the prior ticket. Have the owner submit the new reset token to `POST /api/auth/reset` with `newPassword`.

Passwords contain 12–128 Unicode characters, with whitespace preserved. Asynchronous scrypt uses N=131072, r=8, p=1; two jobs may run and four may wait, with overload returning 429. Sessions expire after 30 minutes idle or 12 hours absolute. Logout revokes its session; reset issuance, deactivation and successful password changes revoke all of the member's sessions. Login rejects unknown, unactivated, disabled and incorrect-password accounts with the same response. Five failed login attempts per account/IP or ticket attempts per endpoint/IP within 15 minutes return 429.

Every write requires the configured Origin. Authenticated writes also require the session-bound `X-CSRF-Token` returned by login or `GET /api/auth/session`, plus an `Idempotency-Key`. The session endpoint recovers the same CSRF token across tabs. Member reset/deactivate actions require `expectedVersion`. Current identity and permissions are checked inside the mutation transaction before replay. Password-change command bindings use the secret session token as an HMAC key; successful changes revoke the key's session, so retries need a fresh login. Secrets are excluded from events and persisted command responses. Request logging is disabled.

Project API: authenticated members can use `GET /api/projects` and `GET /api/projects/:id`. Administrators create projects with `POST /api/projects` (`name`, optional `description`), change roles with `PUT /api/projects/:id/roles` (`memberId`, `roles`, `leads`, `expectedVersion`), and archive or restore with `POST /api/projects/:id/archive` or `/restore` (`expectedVersion`). Roles are `product`, `frontend`, `backend`, and `test`; each lead must also hold that role. Project versions cover role and archive changes. Archived projects preserve reads and reject business writes. An administrator's identical archive retry returns its original response without another event; a new archive command on an archived project conflicts. Current session and permissions are checked before replay.

Shared action policy uses the stored task `kind` as functional scope for `frontend`, `backend`, and `test`; Bug and `other` task services must persist a valid `role` scope. Missing scope denies scoped claim, execution and lead management. `ownerId` controls execution, `acceptorId` controls designated product acceptance, and `authorId`/`participantIds` identify contribution ownership/participation. `manageReport` on a project authorizes draft creation; object-level editing requires `creatorId`. The workflow services validate current status, assignment eligibility and acceptance independence inside each mutation. Future contribution and report services must additionally validate authorship and report ownership. Scope and ownership fields must be derived from stored records, never caller overrides.

Task API: active members can read `GET /api/tasks` and `GET /api/tasks/:id`.
`POST /api/tasks` accepts projectId, title, kind (frontend/backend/test/other),
definitionOfDone and priority, plus optional requirementId, ownerId and reviewerId.
The other kind requires an explicit frontend/backend/test role. Tasks default to
required; product alone may exclude one with required:false and exclusionReason.
Empty definitionOfDone is allowed for a pending draft and must be refined before
execution. Product or the matching functional lead creates/refines tasks, assigns
owners and designates reviewers. Tasks with frontend/backend functional scope,
including explicitly scoped other tasks, require a test-role reviewer.
Test-scoped tasks require product or the matching functional lead to review.

`POST /api/tasks/:id/actions` requires the unchanged expectedVersion and an
Idempotency-Key. Actions: claim (does not start), start, submit, checkPass,
checkFail, assign, transfer, requestTransfer, reopen, cancel, block, unblock,
setDependencies, refine, designateReviewer, setRequired and approveParallel.
Submit evidence is `{done,selfCheck,environment}`; check evidence is
`{result,environment}`. Assign/transfer require ownerId, reason and handoff;
ownerId:null requires resetToPending:true. Transfer otherwise retains state.
Executors can request transfer with reason/handoff. Block requires reason and
assistance; unblock requires reason and retains state. Dependencies are explicit
same-project dependencyIds; unfinished predecessors require a matching current
functional lead's approveParallel action with reason. Approval is bound to task
execution fields and dependency versions and expires when they change or that
lead loses authority. setRequired requires product and a reason; exclusions keep
that reason. Reopening required completed work regresses its requirement in the
same transaction. Work and check evidence are immutable and preserve original
contributors and display names; check records mark actual developer self-tests.
Successful task retries return their original snapshot after current authority
and scope checks, including after the parent advances to pending or accepted;
fresh execution commands still require a ready or active parent.

Bug and canonical test API:

- `POST /api/bugs` registers an unconfirmed project issue with title, explicit functional `role` (frontend/backend/test), expected/actual/reproduction/environment, independent severity and priority. Incomplete reproduction text is permitted while unconfirmed. Optional requirement/task links must agree and belong to the project. Assigning an initial owner requires product or matching lead authority.
- `POST /api/bugs/:id/actions` uses `expectedVersion` and `Idempotency-Key`. Confirmation/rejection/reopen require current test or product authority; repair claim/start/submit require matching scope and actual ownership. Reject reasons are `duplicate`, `not_defect`, `unable` plus explanation; duplicates reference a distinct same-project Bug. Reopen requires reason and explicit `ownerId` (null leaves ready/unassigned). Management assign/transfer requires reason/handoff; null ownership requires `resetToReady:true` and preserves unconfirmed state until the normal confirmation action. Block requires reason/assistance, unblock reason. Reporter supplementation uses `refine` while unconfirmed. `submit.evidence` contains fix, impact, selfCheck, environment and nonblank targetVersion. Verification uses `test` below, not a caller-owned status or selfTest flag.
- `POST /api/tests` takes expectedVersion plus `{target:{kind,id}, revision?, targetVersion, environment, checks:[{checkId,result:'pass'|'fail'|'untested',note?}], reusedFromId?,reuseReason?,bugId?}`. Requirement revision is mandatory for linked targets and absent for independent targets. Actor, actual time, event sequence, original names, ownership, check definitions and selfTest are server-derived immutable evidence. Direct tests enforce the same current designated reviewer, scope, state and submitted build as action routes. Failure on completed work reopens it atomically. Partial evidence remains pending; omitted checks never pass. The caller may associate a same-project existing Bug rather than creating a duplicate defect.
- `GET /api/bugs`, `/api/bugs/:id`, `/api/tests` (optional kind/id) and `/api/tests/coverage?kind=...&id=...&revision=...&targetVersion=...` serve active members. Coverage uses the latest event sequence per exact target/revision/build/check, and checks current definitions. Older passes cannot override newer fail/untested; another target or build cannot supply coverage. Coverage is test evidence only, not product acceptance.
- Independent Bugs default to required check ID `reproduction` (expected behavior); tasks default to `completion` (definitionOfDone). Product-only `defineChecks` on Bug/task sets a nonempty explicit checklist `{id,text,required?,exclusionReason?}[]`, with required default true. Requirement criteria likewise default true; exclusions require product authority and a nonblank persisted reason. Changed definitions invalidate previous coverage. Reuse requires the same target/build/environment, actual source check/result, explicit tester reason, unchanged definitions and no affected check across every intervening requirement revision/scope; later contradictory results for that check/build across the source, intervening and current revisions reject reuse. A fresh real execution can supersede a failure.
- Task submission may add `evidence.targetVersion`; canonical `checkPass`/`checkFail` supply `test`. Tasks with an explicit checklist or submitted targetVersion reject coarse-only checks. Existing legacy submissions/check routes remain compatible and their immutable `task_checks` history is preserved; they never create canonical criterion evidence. Acceptance must use canonical coverage explicitly. No old row is rewritten or inferred as a canonical pass. The acceptance API applies the complete gate and waiver-aware reconciliation described below.
- Bug repair under a cancelled requirement remains a project issue and preserves historical participation links. If cancellation detaches its linked task, the retained Bug source pair remains usable only when immutable prior Bug creation and server cancellation/detachment events prove that relationship; new or arbitrary mismatched pairs reject. Repair never revives the cancelled requirement. The first linked Bug start moves a ready requirement to active in the same transaction. Claim/assignment do not count as repair; successful start and submission append actual repair occurrences. Verification is an independent record, including when the repairer has test authority.


Requirement API: active members read `GET /api/requirements`, `/api/requirements/:id` and `/api/requirements/:id/revisions`. Product or the matching functional lead creates and refines drafts; only product designates the acceptor and confirms readiness. `POST /api/requirements/:id/actions` supports suggestChange, refine, makeReady, start, revise, cancel and restore, with expectedVersion and Idempotency-Key. makeReady requires confirmed source status (checked timestamp or unable reason), a live independent product acceptor, required criteria and execution standards. Editorial revise preserves the functional revision; behavior revise requires reason, impactConfirmed, affectedTaskIds and affectedCheckIds, advances revision and invalidates affected evidence. Cancellation explicitly cancels or detaches every unfinished linked task; Bugs remain open. Restore returns to refining without restarting tasks. Immutable revisions and scope snapshots preserve prior facts.

Product acceptance API (workflow backend; the Vue client remains a scaffold):

- `POST /api/requirements/:id/submit-acceptance` takes `{expectedVersion,revision,targetVersion}`. Product or the requirement's matching functional lead submits active work. The target build is fixed on the pending acceptance round.
- `POST /api/requirements/:id/acceptance` takes `{expectedVersion,decision:'pass'|'return',revision,targetVersion,criteria:[{id,passed,note?}],reason?,reworkTaskIds?,bugIds?}`. Only the currently designated, active product acceptor decides. Actual immutable development/repair participation disqualifies that person, including historical detached or reassigned work; roles and assignments alone do not. A pass requires pending acceptance and every current criterion explicitly passed. Return requires explained failed criteria and existing linked unfinished rework tasks or open Bugs. It also supports recording the return after a regression has already made that submitted scope active, or returning previously accepted original-scope work. `GET /api/requirements/:id/acceptance` returns immutable decisions and their scope/evidence snapshots.
- Both submission and pass re-read confirmed scope, required task completion and current owners/reviewers, exact current-revision/fixed-build latest required requirement criteria, applicable canonical task checks, linked Bug closure or valid waiver, and all blocking flags. Closed Bugs require canonical coverage at that same revision/build; rejected Bugs preserve their disposition. Legacy coarse task checks never supply requirement criterion coverage. Missing, failed, untested, different-target and different-build records do not pass. Gate failures return 422 with `reasons`; stale optimistic versions return 409.
- `POST /api/requirements/:id/bug-waivers` takes `{expectedVersion,bugId,reason,followUpOwnerId,plan}`. Product can defer an open, unblocked normal/minor Bug with a current matching-role follow-up owner. The immutable waiver binds the server's current requirement revision and Bug version; the Bug stays open. A new command cannot duplicate a waiver for that exact scope/version. Changed Bug versions, changed requirement revisions, invalid follow-up ownership, critical/blocker severity or blocking flags invalidate it.
- Every gate-changing task, Bug, canonical test and requirement action reconciles current pending/accepted state inside its root write transaction. Effective role changes and member deactivation also recheck current eligibility; unchanged role commands retain their no-op behavior. A broken gate returns the requirement to active and retains all old acceptance records. Behavior scope changes return accepted/pending work to refining. Cancelled requirements remain cancelled while retained Bugs continue repair. Reconciliation never promotes work automatically. State, records, events, scope snapshots and idempotent responses commit or roll back together.

Acceptance records describe product decisions, not deployment. This repository delivers foundation and workflow APIs plus a Vue scaffold; attachments, the full user interface and production deployment are separate work.

Work updates and history API:

- `POST /api/updates` takes `{target:{kind,id},workDate,done,next?,obstacle?,contributionType,correctsId?,reason?,expectedVersion?}` and an Idempotency-Key. `contributionType` is `development`, `repair`, `testing`, or `coordination`. The server derives the author from the session. Any active project-role member can record their own first contribution; development requires the matching frontend/backend task role, repair the matching Bug role, and testing a test role. Coordination requires a project role. These declarations do not authorize state actions or change ownership, blocking, or workflow state. Explicit development/repair contributes to the immutable independence ledger; a declaration by the designated acceptor while the linked requirement is pending/accepted rejects with 422 and requires a separate authorized workflow or designation change first.
- Work dates are real calendar dates in Asia/Shanghai. Future dates reject; past dates are labeled `lateEntry`. Recording time and global event seq are server-owned. A correction references the latest immutable update ID, its update `expectedVersion` (not object version), and a nonempty reason. Only its original author can correct it; target and contribution type cannot change. Author name and object/owner/project source snapshot remain original, while correction time and event operator are new. Initial updates omit expectedVersion. Next-step and obstacle text may be empty; text does not drive workflow. Revoked roles, inactive sessions and archived projects block writes and replays.
- `GET /api/updates` returns the caller's latest effective update versions. `GET /api/objects/:kind/:id/history` returns append-only events, before/after values, actor, reason, UTC time and Shanghai local time; all active members can read all projects, including archived projects. Both endpoints take only `limit` (1–100, default 50), `afterSeq` (exclusive, default 0), and `cutoffSeq` (inclusive, initially captured server maximum). Responses are `{items,cutoffSeq,nextAfterSeq}`. Carry the same cutoffSeq across pages; null nextAfterSeq ends traversal. History cursors use event seq; own-update cursors use the original logical entry seq (`originalSeq`), so corrections never move an earlier entry behind later contributions. Each effective version also exposes its own `recordedSeq`. Query errors return 400 and database failures return errors, never empty success.
- Internal read-only helpers are `effectiveUpdatesAt(db,cutoffSeq)` and `stateAt(db,target,{time,seq})`. Updates select the latest version of each logical ID at the inclusive seq cutoff before report-date filtering, preserving distinct entries ordered by originalSeq. Snapshots expose requirementId (self for requirements, parent for linked work, null for independent work) and the functional revision resolved from that requirement at the same cutoff; object version remains a separate concurrency field. Later revision or detachment never changes an earlier snapshot. Historical object reads use canonical state events and member/project name events, excluding evidence-only events and current mutable rows. Both time and seq bounds are inclusive; a local report day ends at next midnight minus 1 millisecond, additionally bounded by the generation seq. Missing historical facts remain null rather than being invented from current values.
- Administrators can `POST /api/members/:id/rename` with `{expectedVersion,displayName}` and `POST /api/projects/:id/rename` with `{expectedVersion,name}`. These preserve stable IDs/login, append rename events, support optimistic versions/idempotency and avoid events for unchanged names. Archived projects reject rename. No previous event, contribution or evidence snapshot is rewritten.

Daily report API (deterministic backend; no external AI or messaging integration):

- `POST /api/reports` takes `{date,memberIds,projectIds,timeZone?,previousReportId?,expectedVersion?}`. The default timezone is `Asia/Shanghai`; a real IANA zone and calendar date are required, future dates and nonexistent local days reject. Member/project arrays contain 1–100 unique existing IDs and preserve display order. Any active member may select other members and archived projects without execution roles. To regenerate an existing series, use its latest version ID as `previousReportId` and that version's `expectedVersion`; creator, date, timezone and ordered selection must match. Omit both fields for a new series. Generated text is limited to 190,000 UTF-16 code units, reserving 10,000 for reviewer notes within the 200,000-unit edit limit. Oversized generation/regeneration returns422 with guidance to generate separate reports with fewer members or projects; it saves no draft or replay key and never truncates contributions. This capacity constraint can require splitting very long reports; a single member/project day above the limit cannot be generated as one draft. Both limits are exported as `REPORT_TEXT_LIMITS` in shared contracts for UI capacity display. All writes require session, Origin, CSRF and Idempotency-Key, with current identity and ownership checked before replay.
- `POST /api/reports/:id/versions` takes `{text,expectedVersion}` and appends a creator-only manual draft against the latest series head. Text preserves newlines and supports 1–200,000 UTF-16 code units (nonblank, valid UTF-8, no unsafe control characters); this route alone permits a 1 MiB request body. It never edits source updates or business events. Previous drafts and their source snapshots remain immutable. A stale writer gets 409 with the latest report. Regeneration also appends a version and sets `edited:false`; it never silently replaces an edited draft.
- Write/read results are `ReportVersion`: `{id,seriesId,version,creatorId,input,generatedAt,createdAt,sourceCutoffSeq,stateCutoff:{time,seq},sources:[{kind,id,version,seq}],text,edited,counts:{tasksDone,bugsClosed,requirementsAccepted},reopenedIds}`. `input` stores the normalized date/timezone/ordered selection, without the previous version pointer. `generatedAt` and all source cutoff fields stay unchanged for a manual edit; `createdAt` records each appended draft's actual time. Business event seq and report pagination seq are distinct domains.
- `GET /api/reports` lists all immutable saved versions across series, in append order. `GET /api/reports/:id` retrieves that exact version. `GET /api/reports/:id/versions` lists that version's entire series. `GET /api/reports/:id/sources` reads the saved source snapshot, including distinct effective work updates with original snapshot/author, cutoff object states, attributed state/test/acceptance events, and historical selected names. All active members may read these routes, including archived-project reports. List/version/source routes accept only `limit` (1–100, default50), `afterSeq` (default0), `cutoffSeq` and return `{items,cutoffSeq,nextAfterSeq}`. Report/version cursors use the independent report append seq; source cursors use one-based positions in that immutable source list. Carry the returned cutoff and next cursor, not an entry's business event seq, to the next page. A null cursor ends traversal.
- `GET /api/reports/:id/source-changes` returns `{changed,message,checkedAt,sourceCutoffSeq,added,removed,updated}`; reference arrays use `{kind,id,version,seq}`. A changed selection shows `有更新可重新生成`. It detects additions, corrections and updates moved into/out of the original date selection, never mutates an old draft, and ignores report-only edits. Read/query failures return errors rather than an empty report. Unknown query/body fields reject.
- Generation captures the server time and maximum business event seq and saves its complete source snapshot, report text and idempotent response within one SQLite immediate transaction. Work updates select the latest logical version at that seq **before** filtering by workDate; all logical contributions survive, with original entry order inside stable object-ID groups. State events must satisfy both seq and actual UTC-time cutoffs. Past days end at next local midnight minus1ms; today's cutoff is generation time. Local boundaries respect DST, including 23/25-hour days. Late entries never backdate actual state transitions. Missing historical names remain null/ID display when immutable evidence cannot establish them.
- Counts explicitly describe the **selected state operators**, not the current owners or prose authors. A same-day terminal entry (`task:done`, `bug:closed`, `requirement:accepted`) counts once per object only when its operator is selected and its cutoff state remains terminal. Same-day completion followed by reopening with a nonterminal cutoff state enters `reopenedIds` if either the completion or reopening operator was selected. A terminal entry from an earlier day does not enter that bucket. Authored contributions, test/product state operations and owner-at-cutoff blocked attention remain separate. Testing never becomes a claimed development contribution, and prose never infers completion or deployment. Missing updates show `未填写今日工作更新`; missing plans show `未填写`.
