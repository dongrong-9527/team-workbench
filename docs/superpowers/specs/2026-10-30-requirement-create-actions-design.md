# 新建需求双动作（用户已批准）

用户已批准“保存草稿 / 提交为可执行需求”，并接受正式提交成功即待开始、随后上传截图、图片失败补传不撤回；其他成员可能已开始处理。后续沟通须先以用户视角说明入口、权限、填写、两个动作、失败与成功去向。原云端 checkout/功能分支，基线 HEAD4d682c71 / app954fc7b；本轮不部署、不合并main、不访问Mac。

产品新建弹框提供返回、保存草稿、提交为可执行需求；岗位负责人仍只有既有草稿创建能力。草稿保留标题/来源及原类型、长度等最低校验，普通暂存仍是当前浏览器防丢副本。正式提交还需细化说明、至少一个必需验收条目、有效独立产品验收人、明确来源核对结果。已有字段复用，仅新增来源结果（不默认选）和无法核对原因；checked与unable+原因均合法，checked时间由服务器生成。来源结果不因恢复普通草稿而视为已确认，实质内容改变清掉确认；未知请求仍绑定原已发送命令。来源unable单独显示“无法核对”，不沿用Bug“无法复现”文案。

推荐并批准后端一次原子创建可执行；不采用前端create/refine/makeReady三次请求（会留下半成品与多个恢复阶段）。创建接口新增可选intent=draft|ready，省略按draft。ready严格产品权限、当前成员/归档及原完整门禁。共享门禁保持原makeReady版本/权限/状态限制；不嵌套mutate。失败无对象/快照/事件/幂等残留；不自动降级草稿。成功新对象version1/revision1/state ready/scopeConfirmed true，保留created事件兼容创建者读取，审计明确创建时确认及最终来源信息，不伪造细化历史。无SQL迁移或新后台草稿系统。

提交方式进入命令正文与指纹，未知结果冻结两动作/改写，重试使用原正文/键/方式；已未知请求之后的403等拒绝不消除未知。对象保存成功才上传图片，每图保留原键与版本，成功项不重复；部分失败明确需求实际保存状态及待补传数量，ready不撤回。恢复回执先核对服务器，不把恢复前状态冒充当前状态。保留真实Modal、关闭/路由/焦点/暂存保护及旧折叠筛选。

技术取舍：可选intent属于新API输入契约，旧客户端→新API兼容；新正式提交→旧API应明确拒绝，禁止悄悄草稿回退。新数据仍是原有ready/source/范围快照，审计额外元数据为加法。成对回退前核对未知请求，保留原命令，确认已提交对象；旧UI没有新动作，不能解除未知再创建。
