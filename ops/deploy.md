# Candidate deployment procedure (operator approval required)

These files prepare a release. They do not authorize server access, installation, migration, firewall/SELinux changes, a deployment or a main-branch merge. First obtain the actual Alibaba Linux 4 architecture, glibc/libstdc++, CPU instruction support, disk layout and resource limits. Debian cloud validation does not certify that target.

1. Run `ops/preflight.sh` read-only as the intended service account. Inspect `/etc/os-release`, architecture, GNU libc, memory/disk, listening sockets, installed packages and the machine's actual configured software repositories. Do not assume CentOS/EPEL or a dnf module. Confirm domain, certificate chain/renewal, HTTPS ingress, administrator activation and approved independent backup destination/key custody with the owner. Do not disable SELinux or the firewall.
2. Build outside the production host. Pin `.node-version` (24.21.0) and install lockfile dependencies with TLS verification intact. The API compiler is TypeScript 7; Vue SFC checking deliberately uses the isolated `typescript-sfc` TypeScript 6 alias via `scripts/typecheck-web.cjs`. Do not unify these major versions without a separate compatibility change. Build-host memory is not a production-server requirement.
3. Install production dependencies in a compatible Linux environment using `npm ci --omit=dev --include=optional --workspaces=false`. Keep native optional sharp/libvips platform packages. Record build-image digest and runtime details in `runtime-provenance.json` (`nodeVersion,nodeABI,arch,platform,buildGlibc,buildImage`) beside that directory's `node_modules`; copy its official Node binary and exact-version LICENSE (`node-LICENSE`) there too. Reference cloud image: official `node:24.21.0-bookworm`; record the resolved digest for each build. Native library versions are better-sqlite3 13.0.3 / SQLite 3.53.4 and sharp 0.35.5 / libvips 8.18.7. See [official Node image](https://hub.docker.com/_/node) and [sharp requirements](https://sharp.pixelplumbing.com/install/). Linux x64 sharp requires SSE4.2 and glibc >=2.28; measured ELF symbol requirements of the complete artifact take precedence over this minimum. A successful Debian build is not an AL4 result.
4. Run `npm run build`, then `npm run package:release -- SOURCE FRESH_OUTPUT PROD_DEPS NODE_BINARY VERSION`. Output must be outside the source repository and not exist. The artifact includes the exact Node executable, compiled API/backup/restore/migration/runtime-verifier scripts, trusted migrations, static files and Linux production dependencies. It excludes application tests, fixture generators, environment files, databases, uploads, credentials, dependency tests and build caches. Production dependencies retain their required JavaScript and license files. No runtime npm install is needed. Record a separate archive SHA-256 after creating an archive; the manifest's `sha256` is the SHA-256 of canonical `JSON.stringify` of all other manifest fields, not a self-referential archive hash. Keep the trusted original manifest/archive digest in the authenticated delivery record. Hashes detect changes; they do not authenticate malicious replacement of both content and hashes.
5. Use only this unpacked package to run `runtime/node apps/api/dist/scripts/verify-runtime.js PACKAGE_ROOT`. It verifies exact Node/ABI/platform/architecture, minimum glibc, CPU, every regular file/hash/size, SQLite version and actual SQLite/sharp native load. Native loading checks libstdc++ linkage; the measured GLIBCXX requirement is recorded for target inspection. Reject missing, modified, extra or symlinked files. Validate on the actual target before scheduling deployment.
6. After explicit approval, provision a dedicated nonroot `workbench` account, immutable root-owned `/srv/workbench/releases/VERSION`, `/srv/workbench/current` symlink, writable service-owned `/var/lib/workbench`, private attachments and backup staging, and root-owned `/etc/workbench/runtime.env` (0600). The account must not write release files. Install the reviewed systemd unit and templated Nginx config using the target's supported package/service procedures. Set APP_ORIGIN to exactly the external HTTPS origin. Single Node process binds 127.0.0.1:3000; Nginx serves `/public` and proxies `/api/` on the same origin. No data directory is served statically.
7. Nginx's 6 MiB request ceiling permits bounded multipart overhead around the application's authoritative 5 MiB image input/output cap. Business JSON is capped at 4 MiB, report edits at 1 MiB, other JSON defaults to 16 KiB. Tighten the proxy ceiling if the configured attachment cap is lower. Runtime attachment options and private backup variables are described in `ops/backup.env.example`. Confirm Nginx temporary-body storage capacity/permissions. Test syntax with `nginx -t` and the target systemd with `systemd-analyze verify`; an isolated substitute can validate syntax only, not target installation.
8. Before the maintenance window, generate a Task11 online backup and verify its complete schema, hashes, images and report replay in a fresh scratch directory. Obtain the independently received, authenticated encrypted off-host copy and successful decrypt/restore proof; local directories do not satisfy this gate. During the approved window pause writes and stop the old process; retain the current DB and images. Review every migration for additive compatibility with previous code. Run the new package's `migrate-release.js` only with explicit `MAINTENANCE_CONFIRMED=yes` and DATABASE_PATH. Production server startup never migrates automatically. No automated downgrade exists.
9. Change the release symlink atomically, start the service, verify public `/api/health/live` and `/api/health/ready`, and authenticate an administrator for `/api/admin/runtime`. Public responses contain status only; ready checks exact migration ledger and attachment directory permissions plus database access. It is not a durability/capacity guarantee: independently monitor writable-volume free space, quotas and backup age. Test login, role denial, one reversible synthetic business write, history, attachment and report access before admitting ordinary writes. A failed ready check must block rollout; logs/errors do not reveal environment contents or database paths.
10. Roll out only after full cloud checks and the separately pending target/off-host/owner gates pass. `ops/logrotate.conf` rotates query-free Nginx access logs; configure journald size/retention under the existing operator policy. No request-body, cookie, password, session token or CSRF logging. Track health failures, restart counts, OOM, lock waits, capacity and overdue backup receipts. Rehearse recovery against real operational RPO/RTO objectives before promising them.

## Reproducible cloud verification

Ordinary CI remains `npm test`, `npm run typecheck`, `npm run build`, `npm run e2e`; it does not run a 30-minute benchmark per push. On a clean committed source, first build the tools, then `npm run verify:release:checks -- PRIVATE_CHECKS_DIR` runs those four checks serially and hashes their actual logs. Use the same commit to package and run the separate fault/load harness; see `docs/verification/mvp-checklist.md`.

`npm run verify:release -- PRIVATE_CHECKS_DIR PACKAGE_ROOT LOAD_JSON DRILL_JSON` requires all actual evidence, exact commit/runtime/package binding, matching report/log hashes and timestamps within seven days. Missing, failed, too-short or unconstrained checks return nonzero. This is a local evidence gate, not a cryptographic attestation service; preserve its private measurement files against replacement. No production deployment is performed by any command here.
