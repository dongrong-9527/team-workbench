# Rollback preserving current writes

Prefer a forward fix. A code rollback is allowed only after checking that the previous executable supports the current schema and all newly stored values. Stop writes, preserve a fresh current database+attachment snapshot, verify it in an isolated directory, retain both release directories and change only the executable symlink. Restart against the current database and run authenticated business, image and report checks. Additive migrations do not automatically prove old-code compatibility; record the reviewed compatibility decision.

Never overwrite the current database with the deployment's older backup after new writes. That loses acknowledged work. If code rollback cannot read the current schema, keep writes stopped, preserve the current database/WAL/images as well as a verified online snapshot where possible, quantify the differences from the old snapshot, and obtain a separate explicit recovery decision from the owner. Restore only into a fresh isolated location until that decision. There is no automatic database downgrade, old-snapshot copy, destructive restore or delete command in these instructions.

The synthetic `rehearseRollback(scratchDir)` takes an old snapshot, acknowledges another task change, then preserves/verifies the current database in isolation and checks its object version and idempotency record. This proves the rehearsal's preservation policy, not compatibility of an arbitrary previous release. The package drill additionally restores an image/report and performs a real authenticated write against the isolated restored application. A different directory on the same host is local recovery evidence only. Off-host encryption, custody, transfer, receipt and independent restore remain required operator gates.
